Reference guide · securesbom-attestation-v1

Connect the dots from signing to verification.

An attestation binds an SBOM to the exact artifact it describes. This guide walks through the four messages in that flow, shows what each field means, and lists what to check before you trust the result.

Download PDF Try it in your browser Why bind the SBOM to the artifact?

The flow

Four messages, one chain of trust

The producer signs once. Every consumer verifies with a digest they computed themselves. Select a step to open it in the explorer below.

What is inside the attestation

DSSE envelope payloadType, payload (base64), signatures[]. The ES256 signature covers the PAE: DSSEv1 <len> <type> <len> <payload>
in-toto Statement v1 (RFC 8785 canonical JSON) _type, predicateType
subject[] Artifact name and sha256 digest. This is the binding.
predicate The SBOM itself (CycloneDX, SPDX or AI-SBOM)
signature Optional embedded SBOM signature, so the SBOM stays verifiable on its own

Checklists

  
What to check, message by message

  

    

      
1 · Sign request

      
Before you sign

      
    
        
  • The key_id belongs to a key created with key_type: "attestation". Standard signing keys are rejected with key_purpose_mismatch.
    • 
        
  • subject[].digest.sha256 is the digest of the artifact (an image manifest, a binary or a package), not of the SBOM. It is 64 lowercase hex characters.
    • 
        
  • subject[].name identifies the artifact the way consumers will look it up, such as an image reference or package URL.
    • 
        
  • sbom is a JSON object, not a string. It must not already carry a signature, and it must not contain integers above 253 or duplicate keys.
    • 
        
  • Pick predicate_signature on purpose: embedded (the CycloneDX and AI-SBOM default), detached (the SPDX default) or none.
    • 
      

    

    

      
2 · Sign response

      
Before you publish

      
    
        
  • Store and distribute attestation exactly as returned. Never re-encode or pretty-print the payload, because the signature covers those exact bytes.
    • 
        
  • Decode payload and confirm the subject name and digest are the artifact you meant to sign.
    • 
        
  • predicate_type matches the SBOM format: https://cyclonedx.org/bom, https://spdx.dev/Document or https://shiftleftcyber.io/attestation/ai-sbom/v1.
    • 
        
  • signatures[0].keyid equals your key_id, and algorithm is ES256.
    • 
        
  • Record statement_sha256. The verify response returns the same value, which makes audit trails easy to join.
    • 
        
  • In detached mode, keep the returned predicate signature with the attestation. Verifiers need it.
    • 
      

    

    

      
3 · Verify request

      
Before you verify

      
    
        
  • Compute expected_digest.sha256 yourself from the artifact you are about to run. Never copy it from the attestation, or the check proves nothing.
    • 
        
  • Send attestation as a JSON object, not as a quoted string or a wrapped field.
    • 
        
  • Use the key_id of the producer you expect. Verification is pinned to that key, and a different signer fails with key_mismatch.
    • 
        
  • For a detached attestation, include the producer's predicate_signature.
    • 
      

    

    

      
4 · Verify response

      
Before you trust it

      
    
        
  • Gate on verified: true. Anything else returns an error code that names the first check that failed.
    • 
        
  • checks reports each layer separately: signature, payload_canonical, subject_match and predicate_signature.
    • 
        
  • matched_subject is the artifact your digest matched. Confirm the name is the one you expect.
    • 
        
  • key_type is attestation and predicate_type is the SBOM format you expect.
    • 
        
  • statement_sha256 equals the value from the sign response.
    •

    Troubleshooting
    
  
    Verification error codes
    
  
    
    
    
      
    CodeWhat it meansWhat to check
    
      
        
    expected_digest_requiredThe request has no expected_digest.sha256.Hash the artifact you are about to use and send that digest.
    
        
    invalid_envelopeThe attestation is not a well-formed DSSE envelope with the in-toto payload type.Send the envelope as a JSON object, unchanged, with payloadType, payload and signatures.
    
        
    key_mismatchThe envelope was signed by a different key than the key_id you asked for.Confirm which producer key you expect, and check signatures[].keyid.
    
        
    signature_invalidThe ES256 signature does not match the PAE of the payload.The payload or signature changed after signing. Re-fetch the original attestation.
    
        
    payload_not_canonicalThe payload bytes are not RFC 8785 canonical JSON.Something re-serialized the payload, for example by pretty-printing or reordering keys.
    
        
    invalid_statementThe payload is not a valid in-toto Statement v1.Check _type, subject, predicateType and predicate.
    
        
    unsupported_predicate_typeThe predicate type is not CycloneDX, SPDX or AI-SBOM.Confirm the attestation came from a supported SBOM format.
    
        
    subject_mismatchNo subject digest equals your expected digest.You are verifying the wrong artifact, or the artifact changed. Do not deploy it.
    
        
    predicate_signature_invalidThe SBOM-level (embedded or detached) signature does not verify.The SBOM inside the statement was changed, or the wrong detached signature was supplied.
